# Committee Meeting Minutes

Produce concise, useful minutes in the format Richard approved on October 17, 2026. Answer three questions for each topic: What is the update? What is happening next? Who needs to take action?

## Gather the meeting facts

1. Read the supplied agenda and transcript or notes. Reuse the current document when revising minutes; preserve its file identity and earlier corrections.
2. Use the agenda for the meeting date, committee name, section order, and next meeting. Use the transcript for what actually happened. Prefer the user's latest explicit correction over either source.
3. Identify the actual presiding officer separately from the committee chair. Record a chair as present even when another person led the meeting.
4. Record attendance, late arrivals, opening prayer or devotion, approval of prior minutes, motions, decisions, assignments, closing prayer, and adjournment when supported.
5. Read [references/format.md](references/format.md) for the approved organization, visual specifications, and examples. For SPLC meetings, also read [references/splc.md](references/splc.md) for confirmed names and context.

## Write the minutes

- Aim for two readable pages for a typical meeting. Allow more only when necessary to preserve material business; never shrink the text to force a page count.
- Use plain language at about an eighth-grade reading level. Keep each topic to one short paragraph, usually two to four sentences.
- Begin each topic with a bold label. State status, decision, then next action and owner when known.
- Keep material costs, deadlines, quantities, and dependencies. Omit conversational back-and-forth, jokes, speculation, repeated arguments, personal criticism, and unnecessary health or family details.
- Put actions within their related topic. Do not repeat them in a separate action list unless requested.
- Distinguish reports, proposals, recommendations, and approved decisions. Never turn discussion into approval or a suggestion into an assigned task.
- Name the motion maker and seconder when supported. State the outcome only when supported; do not infer unanimity from silence or agreement in discussion.
- Treat budget figures as estimates when that is how they were presented. Do not turn a report of insurance or legal requirements into verified advice.
- Do not invent attendees from unclear speech. Use confirmed names; ask a concise question outside the document if attendance is unresolved.
- Ask only questions that materially change the official record. Keep uncertainty questions in chat rather than adding a Draft items to confirm section. If a fact remains unknown, omit unsupported detail or use a short neutral placeholder only when needed.
- Retain a draft designation until the user requests its removal or supplies approval. Do not mark minutes approved merely because they were reviewed or emailed.

## Produce and revise the document

1. Default to an editable DOCX unless the user asks for another format. Use the available documents skill and its rendering workflow.
2. Apply the typography and layout in the format reference. Keep titles and headings black and remove inherited decorative title borders.
3. Render and visually inspect the pages. Fix overflow, blank pages, clipped text, and awkward breaks before delivery.
4. On a correction, change the requested facts and any now-stale uncertainty notes while preserving other content. Apply later time corrections consistently, including adjournment.
5. Save generated documents through the available persistent file workflow. Preserve the same document identity on edits. Do not publish actual meeting records to a code repository unless specifically asked.
6. Return a short completion message and the document link. Do not narrate routine production details.

## Follow-up actions

Do not automatically send email, create calendar events, or add tasks when asked only for minutes. When explicitly asked to distribute them, use the latest relevant committee correspondence to resolve recipients and honor explicit additions. Attach the current revision, identify it as draft when appropriate, and ask for corrections. When asked to create SPLC Todoist tasks, apply the SPLC label.
